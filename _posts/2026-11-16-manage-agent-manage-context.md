本文是一篇面向产品设计的技术探讨，内容来自 Tacit 的开发实践。文中讨论的是设计判断与取舍，不是对现有产品功能的完整介绍。

## 1. 问题：多任务的上限是人的注意力

过去一年的 Coding Agent 已经证明，模型可以在单个任务上长时间自主工作。但当用户并行推进多项工作时，主流产品的组织方式仍然是：每个任务一个 Session，Session 之间彼此独立。

这种设计把两类成本转嫁给了人。一是上下文搬运：A 会话的结论要复制给 B，B 需要的背景要从与 C 的历史对话里重新讲一遍。二是状态记忆：哪个会话进行到哪一步、哪个结论还有效，都要人来记。人在会话之间来回切换，扮演消息路由的角色，真正用于思考方向的时间反而被压缩。

认知研究里有两个常被引用的结论可以解释这种成本：人被打断之后，平均需要二十多分钟才能重新回到之前的状态（Gloria Mark）；即使切换完成，注意力仍会粘在上一件事上，即"注意力残留"（Sophie Leroy）。在多个 Agent 之间传话，恰好是最高频的切换。

一个粗略的观察是：一个人能同时有效跟进的活跃会话不超过 3 到 5 个。换句话说，单任务的上限取决于模型能力，多任务的上限取决于人的注意力。要提升后者，需要改变的是上下文的管理方式。

## 2. 一个更简的抽象：上下文与模型

先回答一个问题：Agent 是什么。

我们的看法是：Agent = 一份上下文 + 一个模型。对话不是交流，是一个持续注入内容的 Session；一个 Project 里的多个对话围绕同一主题，和多个 Agent 围绕同一任务，本质上是同一件事的两种形态——它们都在回答同一个问题：这一次推理，模型看到什么。

把问题归约到这一层之后，很多设计争论会消失。今天的多 Agent 产品大多把"团队"作为默认抽象：分工、频道、工单、@。这些机制在人类组织里是必要的，因为人的记忆不能共享，只能靠语言压缩和会议对齐。Agent 没有这种限制——给它读同一份上下文即可。把为人类局限设计的机制照搬到 AI 上，多数时候是在解决一个不存在的问题。

## 3. 跨 Agent 通信的损耗

多 Agent 架构最常见的理由是分工，但通信本身有成本。

人与人传话会失真，因为记忆无法共享，只能压缩后复述。Agent 之间如果不共享底层上下文，也要走同样的"压缩—复述—再理解"路径，每传一次就多一分损耗。另一个问题是隐性决策：每个 Agent 的行动都基于它对任务的局部理解，两个 Agent 基于不同假设各自行动，产出往往互相冲突，最后由人来发现和收拾不一致。

还有一个常被高估的因素：Agent 与 Agent 之间的差异，通常远小于模型与模型之间的差异。产出质量更多由底层模型决定，而不是由"角色"决定。多数情况下，把任务分给五个 Agent，不如把上下文给对一个 Agent。

## 4. Fork 与共享上下文

这解释了为什么多数时候 fork 比新建 Agent 好用：fork 是共享，新分支天然拥有主对话的全部历史；多 Agent 是传递，历史被压缩、复述、再理解。传递每多一层，损耗就多一分。

但 fork 有自己的边界：主对话会持续膨胀。自然生长的上下文里，闲聊、过时结论和中间过程的噪音都留在窗口内，持续消耗模型的注意力；长上下文下的召回精度也会下降。靠对话生长出来的上下文，质量往往越来越差。

所以上下文更可靠的来源是设计而不是生长：围绕任务的结构，在一开始就确定哪些信息必须在场、以什么形式在场。

## 5. 设计原则：全面的上下文，包裹的细节

从上面的分析里，我们沉淀出两条原则，少到不像产品理念。

第一，全面的上下文是必须的。AI 要接得住任务，前提是它看得到足够全的材料：该汇入的信息源持续汇入，该记住的进展持续记住。上下文缺一块，执行就歪一块，而且往往要到结果出来才被发现。

第二，细节是需要包裹的。上下文怎么组装、缓存在哪一层命中、token 怎么省，都应留在系统内部。这不只是体验问题，也是成本问题：保持注入内容的前缀稳定，就能命中 KV 缓存，命中与不命中的推理成本通常差一个数量级。一份长期维护、结构稳定的任务上下文，同时带来更便宜和更快。用户侧能感知的只有结果：它懂我，它快，它不贵。

## 6. Goal 文件与 Loop

执行可以完全信任给 AI，但验收必须明确。每个任务都要能说清"什么叫做完、什么叫做得好"，并且真的照着检查。信任不等于放任。

落到结构上，Tacit 的做法是：每个项目、每个任务对应一个 goal 文件，内容是这个任务的全部上下文——目标、材料位置、验收标准、当前进展。围绕它的运行是一个 loop：每次对话注入 goal 文件，执行，更新文件，按文件里的标准验收。这个 loop 是产品最核心的运行机制；goal 文件是唯一需要长期维护的对象，执行体本身是易失的，每次运行时重新注入即可，不需要维护。

## 7. 与现有产品的关系

自动收集上下文并不是新想法。Screenpipe、AirJelly、Littlebird，以及 Codex 内置的 computer history，都做过类似的事。但它们大多停在"收集"：信息存了下来，没有进入行动的回路。Tacit 想打通的是从 context 到事件的循环——收集到的每一条上下文，都要成为下一次行动的依据。

组织方式上，Multica、Raft 通过群聊和工单提供了可行的多 Agent 组织方案，底层抽象也做得比较完整，Tacit 借鉴了它们的构造方式。区别在于：它们把任务划分和上下文构建留给了用户，而 Tacit 试图让 AI 自己完成这一层。Claude Projects 的形态接近，但绑定单一模型。

## 8. 开放问题

这套设计里仍有不少问题没有定论：

- 验收标准的形式化。并非所有任务的标准都能写成可检查的条件，模糊标准下的验收目前仍要退回给人。
- 上下文边界的划分。什么该写进 goal 文件、什么该留在原始信息源里按需读取，直接影响缓存命中率与信息新鲜度，两者存在权衡。
- goal 文件的长期维护。运行周期拉长后，文件自身也会腐化，需要压缩与重写策略。
- 多任务并发时 goal 文件之间的关联与冲突，还没有系统的处理办法。

## 结语

本文没有提出新的概念，做的事是把 context engineering 里已被验证的经验，从单会话推到多任务的产品形态：用 goal 文件承接上下文，用 loop 承接运行，用验收承接信任，把 Session 和组装细节收回系统内部。

产品取名叫 Tacit，来自 tacit knowledge（默会知识）：那些说不清、但一直在起作用的东西。好的协作不需要反复解释——我们希望 Agent 在人开口之前，就已经掌握了相关的上下文。
